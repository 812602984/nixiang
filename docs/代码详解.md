# privacy-scanner 代码详解

> 这份文档假设你**没写过逆向、没读过二进制格式、Python 也只会基础语法**。
> 每一段代码我都按「它在做什么 → 为什么要这么做 → 不这么做会怎样」讲。

## 第零章 先用一句话说清这个工具在干什么

你把一个 App 的安装包扔给它，它拆开，把里面的**清单**读出来，告诉你三件事：

1. 这个 App 申请了哪些**权限**（能不能读你通讯录、能不能定位你）
2. 它集成了哪些**第三方 SDK**（友盟、穿山甲这些，它们会偷偷采集设备信息）
3. 它有没有**穿壳**（加固），穿了哪家的壳

打印成一份人话报告。

类比：**机场安检的行李清单核对**。

- 行李（安装包）先过 X 光机（拆 zip）
- 看申报单（读清单文件）
- 核对有没有违禁品（对照危险品名单：权限表、SDK 特征库）
- 出一份安检记录（报告）

听起来简单。**难点全在"读清单"这一步**——因为这张清单不是给人看的，是给机器看的，长的跟你想的完全不一样。

## 第一章 破除三个误解

### 1.1 误解一：APK 是个"安装包文件"

不是。**APK 本质是个 zip 压缩包**，只是后缀改了。

你可以自己验证：把 `xxx.apk` 改名成 `xxx.zip`，双击就能打开，里面是一堆文件和文件夹。

```
app.apk (其实是 zip)
├── AndroidManifest.xml    ← 清单：这个 App 的身份证 + 权限申请表
├── classes.dex            ← 真正的代码（Java/Kotlin 编译后的产物）
├── classes2.dex           ← 代码太多，分包了
├── resources.arsc         ← 资源索引表（图片、文字、颜色）
├── lib/                   ← 原生 C/C++ 库
│   └── arm64-v8a/
│       └── libxxx.so
├── assets/                ← 打包进去的原始资源
└── META-INF/              ← 签名信息
```

所以工具第一步是 `zipfile.ZipFile(path)` —— 就是"当成 zip 打开"，不是什么高深操作。

### 1.2 误解二：`AndroidManifest.xml` 是个 XML 文件，能用 XML 解析器读

**这是整个项目最核心的认知门槛。**

你在电脑上看到的 `AndroidManifest.xml` 是这样的（明文）：

```xml
<manifest package="com.example.app">
    <uses-permission android:name="android.permission.READ_CONTACTS" />
    <application>
        <activity android:name=".MainActivity" android:exported="true" />
    </application>
</manifest>
```

但**打包进 APK 之后，它被编译成了二进制**。同一个文件，在 APK 里长这样（真实字节，十六进制）：

```
03 00 08 00 A4 12 00 00     ← 文件头
01 00 1C 00 ...             ← 字符串池
02 01 10 00 ...             ← 元素开始
```

**完全读不了。** 你拿 Python 的 `xml.etree.ElementTree` 去解析，它会直接报错，因为里面一个 `<` 字符都没有。

为什么要编译成二进制？

- **省空间**：字符串重复的存一份（`android.permission.READ_CONTACTS` 这种长字符串，几十个权限里前缀重复率极高）
- **解析快**：手机上每次装 App、每次启动，系统都要读这个文件，二进制比文本快得多
- **防篡改**：顺带增加了改包的难度

所以：**必须自己写一个能读懂这种二进制的解析器**。这就是 `parsers/axml.py` 存在的全部理由。

### 1.3 误解三："申请了权限" ≠ "正在偷你的数据"

工具告诉你"这个 App 申请了读取通讯录的权限"，**不代表它真的读了，更不代表它在你同意隐私政策之前就读了**。

这中间有三层：

```
第一层：清单里声明了权限     ← 静态扫描能看到（这个工具做的事）
第二层：运行时真的调用了 API ← 只有动态 hook 能看到（下一个项目做的事）
第三层：调用发生在用户点"同意"之前 ← 这才是违规（需要第二层 + 时间戳对比）
```

**工具只覆盖第一层。** 报告第七章专门写了这句话，不是免责声明，是能力边界。**把边界写清楚，比多列十条功能更可信。**

## 第三章 `axml.py` —— 最硬的一块

这个文件 233 行，是整个项目的技术核心。我按"你拿到一堆字节，怎么一步步读懂它"的顺序讲。

### 3.1 一切皆 Chunk（块）

二进制 XML 的基本单位叫 **Chunk（块）**。你可以理解成**乐高积木**：整个文件是由一块块积木拼起来的，每块积木开头都贴一张标签，写着"我是什么类型、我有多长"。

标签固定 8 个字节，三个字段：

```
┌─────────┬───────────────┬─────────────┐
│  type   │  headerSize   │     size    │
│ (2字节) │   (2字节)      │   (4字节)    │
└─────────┴───────────────┴─────────────┘
   我是什么      我的头多长      我整块多长
```

对应代码：

```python
def _read_chunk_header(data, offset):
    ctype, header_size, chunk_size = struct.unpack_from("<HHI", data, offset)
```

`"<HHI"` 是什么意思？

- `<` = 小端序（little-endian）。**通俗解释**：数字在内存里是从低位往高位存的。`0x1234` 存成 `34 12` 而不是 `12 34`。安卓/英特尔 CPU 都是小端序，所以固定用 `<`。
- `H` = 2 字节无符号整数（对应 type、headerSize）
- `I` = 4 字节无符号整数（对应 size）

**为什么需要 `size` 字段？** 因为要能一块一块跳着读：

```python
pos += chunk_size   # 读完这块，直接跳到下一块
```

就像读书时每章开头写着"本章共 20 页"，你就可以直接翻到第 21 页，不用一页页找章节标题。

代码里定义了一堆类型常量：

```python
_RES_STRING_POOL_TYPE        = 0x0001   # 字符串池（字典）
_RES_XML_TYPE                = 0x0003   # 整个 XML 文件的外壳
_RES_XML_START_ELEMENT_TYPE  = 0x0102   # 一个标签开始，如 <manifest>
_RES_XML_END_ELEMENT_TYPE    = 0x0103   # 一个标签结束，如 </manifest>
_RES_XML_RESOURCE_MAP_TYPE   = 0x0180   # 资源 ID 映射表
```

`0x0003` 出现说明：**整个文件的第一块是"外壳"，告诉你"我是个二进制 XML"**。

```python
ctype, _, _ = _read_chunk_header(data, 0)
if ctype != _RES_XML_TYPE:
    raise ValueError(f"不是 AXML 文件（chunk type=0x{ctype:04x}）")
```

这行是**验明正身**。万一把一个随机文件扔进来，能立刻报错而不是解析出一堆垃圾。这就是为什么后面 APK 解析里能安心调用它。

### 3.2 字符串池：为什么要有个"字典"

这是整个格式设计里最聪明的地方，也是新手最容易卡住的地方。

**问题**：一个 App 的清单里，字符串高度重复。

```
android.permission.READ_CONTACTS
android.permission.WRITE_CONTACTS
android.permission.ACCESS_FINE_LOCATION
android.permission.CAMERA
...
com.example.app.MainActivity
com.example.app.SettingsActivity
com.example.app.AboutActivity
```

每个字符串都要几时个字节。如果每次都完整存一遍，文件会非常大。

**解法**：把所有字符串抽出来，去重，排成一列，编上号。文件里其他地方**只存编号**（数字，4 字节）。

就像一本书后面有"名词索引"：正文里只写 `[12]`，想看第 12 个名词是什么，翻到索引页。

```
字符串池（就是一个数组）：
  [0] "android"
  [1] "http://schemas.android.com/apk/res/android"
  [2] "manifest"
  [3] "package"
  [4] "com.example.app"
  [5] "uses-permission"
  [6] "name"
  ...
```

后面所有地方，需要"manifest"这个词，就写数字 `2`。

**这就是为什么解析的时候，读到 `name_idx = 2`，要去 `strings[2]` 里取真名。**

代码在这里：

```python
def _parse_string_pool(data, offset):
    _, header_size, chunk_size = _read_chunk_header(data, offset)
    string_count, style_count, flags = struct.unpack_from("<III", data, offset + 8)
    strings_start = struct.unpack_from("<I", data, offset + 20)[0]
    is_utf8 = bool(flags & _STRING_POOL_UTF8_FLAG)
```

字段含义：

| 偏移 | 字段 | 含义 |
| --- | --- | --- |
| +0 | chunk 头 | type=0x0001, headerSize, size |
| +8 | string_count | 一共有多少个字符串 |
| +12 | style_count | 样式数量（基本是 0，不用管） |
| +16 | **flags** | 标志位，`0x100` 表示字符串用 UTF-8 存 |
| +20 | **strings_start** | 字符串数据区相对本块开头的偏移 |

**`flags & 0x100` 在判断什么？**

字符串池支持两种编码：

- **UTF-16**：每个字符 2 字节（英文也占 2 字节，浪费）
- **UTF-8**：英文 1 字节，中文 3 字节（省空间）

`0x100` 是个"开关"，置位了就是 UTF-8。所以：

```python
is_utf8 = bool(flags & 0x100)
```

`&` 是按位与。通俗说：**检查第 9 个二进制位是不是 1**。是 1 → UTF-8，是 0 → UTF-16。

**为什么要区分？** 因为两种格式读法完全不同，读错了全是乱码。

接着读偏移表：

```python
for i in range(string_count):
    pos = offset + header_size + i * 4
    offsets.append(struct.unpack_from("<I", data, pos)[0])
```

头部之后紧跟着 `string_count` 个 4 字节整数，每个是"第 i 个字符串相对数据区起点多远"。**这就是"索引页"**：第 0 个字符串在数据区 +0 处，第 1 个在 +20 处……

最后按偏移去取内容：

```python
for rel in offsets:
    pos = base + rel
    if is_utf8:
        _, pos = _decode_length8(data, pos)   # 跳过 UTF-16 长度
        length, pos = _decode_length8(data, pos)  # 真正的 UTF-8 长度
        raw = data[pos:pos + length]
        strings.append(raw.decode("utf-8", errors="replace"))
```

**这里有个坑，必须讲清楚**：UTF-8 模式下，每个字符串前面**有两个长度字段**，不是一个。

- 第一个：这个字符串按 **UTF-16 编码**会有多少字符（安卓为了某些内部计算保留的）
- 第二个：这个字符串按 **UTF-8 编码**有多少字节

所以我们**只需第二个**，第一个用 `_` 丢掉：

```python
_, pos = _decode_length8(data, pos)      # 第一个，不要
length, pos = _decode_length8(data, pos) # 第二个，要这个
```

不跳过第一个会怎样？会把长度字段当成内容读，整个字符串都错位，后面全乱。

**`_decode_length8` 又是什么鬼？**

```python
def _decode_length8(data, pos):
    first = data[pos]
    if first & 0x80:
        return ((first & 0x7F) << 8) | data[pos + 1], pos + 2
    return first, pos + 1
```

长度字段是**变长的**：1 字节或 2 字节。

- 首字节最高位是 0 → 就是这 1 个字节的值（0~127）
- 首字节最高位是 1 → 说明"一个字节装不下"，要连读第二个字节

```
举例：长度 = 200
200 > 127，一个字节不够
存成：  0x80 | (200 >> 8)   然后  200 & 0xFF
     =  0x80 | 0x00 = 0x80,  然后 0xC8
读的时候： (0x80 & 0x7F) << 8 | 0xC8 = 0 << 8 | 200 = 200  ✓
```

**为什么不用固定 4 字节？** 因为字符串通常很短（十几字节），用 4 字节存长度太浪费。变长编码是"能用小的就用小的"，平均省一半。

### 3.3 遇到"标签开始"：36 字节里有什么

读到 `type == 0x0102`（START_ELEMENT），意味着遇到了一个 XML 标签，比如 `<manifest>`。

结构固定 36 字节（不含属性）：

```
偏移  字段              含义
─────────────────────────────────────────────
+0    type=0x0102       我是"标签开始"
+2    headerSize=16     我的头 16 字节
+4    size              整块长度（含属性）
+8    lineNumber        在源码第几行（调试用）
+12   comment           注释索引（几乎都是 0xFFFFFFFF = 没有）
+16   ns                命名空间索引
+20   name              ★ 标签名索引（"manifest" = 2）
+24   attributeStart    ★ 属性区相对本结构体的偏移（通常 20）
+26   attributeSize     ★ 每个属性多大（通常 20）
+28   attributeCount    ★ 有几个属性
+30   idIndex           保留字段
+32   classIndex        保留字段
+34   styleIndex        保留字段
```

代码：

```python
line = struct.unpack_from("<I", data, chunk + 8)[0]
name_idx = struct.unpack_from("<I", data, chunk + 20)[0]
attr_start, attr_size, attr_count = struct.unpack_from("<HHH", data, chunk + 24)
tag = strings[name_idx] if name_idx < len(strings) else f"tag_{name_idx}"
```

**`strings[name_idx]` 就是查字典**：`name_idx = 2` → 去字符串池第 2 个 → `"manifest"`。

#### 这里有一个我踩过的坑，必须讲

属性区的**起始位置不是 `chunk + attributeStart`**，而是：

```python
attr_base = chunk + 16 + attr_start
```

**为什么多出个 16？**

因为 `attributeStart` 的定义是"**相对于 `ResXMLTree_attrExt` 这个结构体的偏移**"，而这个结构体并不是从 chunk 开头算起的——它从 `chunk + 16` 开始（前面 16 字节是 chunk 头和 lineNumber/comment）。

标准值 `attributeStart = 20`，所以真实起点是 `chunk + 36`。

一开始我按 `chunk + attr_start` 算，得到 `chunk + 20`，正好**落在属性名称字段上**，导致：

> 权限名字读出来了，但值是空的。

因为偏移错了 16 字节，`struct.unpack` 把"属性名索引"当成了"值数据"。这就是为什么第一版报告里包名、版本全是空白。

**加了一层保险**：

```python
if attr_base + attr_count * attr_size > chunk + chunk_size:
    attr_base = chunk + attr_start   # 兼容个别非标准生成器
```

如果算出来的位置**超出了这一块的范围**，说明这个文件不是标准格式，退回用旧算法。**宁可读错也不崩** —— 这是解析陌生格式的基本素养。

### 3.4 属性：20 字节塞了 5 样东西

每个属性固定 20 字节（`attributeSize` 通常是 20）：

```
偏移  字段        含义
────────────────────────────────────────
+0    ns          命名空间索引（比如 android）
+4    name        属性名索引（比如 "exported"）
+8    rawValue    原始字符串索引（通常 0xFFFFFFFF = 无）
+12   size        这个值有多大（固定 8）
+13   res0        保留
+14   dataType    ★ 值的类型
+16   data        ★ 值（注意：是数字，不是字符串！）
```

代码：

```python
ns_idx, attr_name_idx, raw_idx = struct.unpack_from("<III", data, a)
val_size, _, val_type = struct.unpack_from("<HBB", data, a + 12)
val_data = struct.unpack_from("<I", data, a + 16)[0]
```

注意 `"<HBB"`：`H` 是 2 字节（size），两个 `B` 各 1 字节（res0、dataType）。

**为什么 `data` 是个数字而不是字符串？**

因为 XML 里属性的值可能是各种类型：

```xml
android:name=".MainActivity"    ← 字符串
android:exported="true"         ← 布尔
android:versionCode="231"       ← 整数
```

二进制里怎么统一表示？**用"类型标签 + 一个 32 位数字"**：

- 如果类型是"字符串"，那个数字就是**字符串池里的索引**，要去查表
- 如果类型是"整数"，那个数字就是**整数本身**
- 如果类型是"布尔"，0=false，非 0=true

`_resolve_value` 就是干这个的：

```python
def _resolve_value(strings, raw_idx, val_type, val_data):
    if val_type == _TYPE_STRING:      # 0x03
        return strings[val_data]      # 数字当索引，去查字符串池
    if val_type == _TYPE_INT_BOOLEAN: # 0x12
        return "true" if val_data else "false"
    if val_type == _TYPE_INT_DEC:     # 0x10
        return str(val_data)          # 数字就是值本身
    ...
```

**这一个函数是"把机器码翻译成人话"的关口。**

```python
val_type == 0x03, val_data == 4   →  strings[4]  →  "com.example.app"
val_type == 0x10, val_data == 231 →  "231"
val_type == 0x12, val_data == 1   →  "true"
```

还有几个不常见但会有：

| 类型 | 值 | 处理 |
| --- | --- | --- |
| `0x01` REFERENCE | 指向资源表 | 输出 `@0x7f010001` 形式 |
| `0x04` FLOAT | 浮点数的位模式 | 把整数重新解释成 float |
| `0x11` INT_HEX | 十六进制整数 | 输出 `0x...` |

`FLOAT` 那行看着绕：

```python
struct.unpack("<f", struct.pack("<I", val_data))[0]
```

意思是：把整数 `val_data` **重新装回**成 4 字节，再按浮点格式**重新解释**。因为 IEEE 754 浮点数就是用一个 32 位整数位模式表示的，同一个 32 位，当整数读和当浮点读，结果不同。

### 3.5 资源 ID 兜底：加固工具把名字抹了怎么办

正常的 APK，属性名（`name`、`exported`）都在字符串池里，能查到。

但**有些加固工具会故意把这些字符串抹掉**，让你的解析器读出一堆空字符串。攻防就是这么来的。

对策：**安卓系统给常用属性分配了固定的数字 ID**。数字抹不掉（抹了文件就解析不了）。

```python
_RES_ID_TO_ATTR = {
    0x01010003: "name",
    0x01010006: "permission",
    0x01010010: "exported",
    0x0101001D: "authorities",
    0x0101021C: "versionName",
    0x0101020C: "minSdkVersion",
    ...
}
```

所以读到空名字时：

```python
attr_name = strings[attr_name_idx] if attr_name_idx < len(strings) else ""
if not attr_name:
    attr_name = _RES_ID_TO_ATTR.get(attr_name_idx, f"attr_0x{attr_name_idx:08x}")
```

**能查表就查表，查不到就原样打印数字**（`attr_0x01010xxx`），至少不丢信息。

这一手很像"密码学里的侧信道"：你藏了 A，但 B 没藏住，我就用 B 反推 A。

### 3.6 Node 类：为什么要两本字典

```python
class Node:
    __slots__ = ("tag", "attrs", "ns_attrs", "children", "parent", "line")

    def __init__(self, tag, line=-1, parent=None):
        self.attrs = {}
        self.ns_attrs = {}   # 来自 android 命名空间的属性
```

**为什么一个节点要存两份属性？**

因为 XML 里同一个属性名可能来自不同命名空间：

```xml
<manifest
    android:name="..."     ← 来自 android 命名空间
    package="..."          ← 无命名空间
>
```

极端情况下，`android:name` 和 `name` 可以同时存在，值不同。我们需要的**永远是 android 那份**（`android:exported`、`android:name` 才是标准属性）。

所以：

```python
if ns_uri == ANDROID_NS or not ns_uri:
    node.ns_attrs[attr_name] = value
```

**android 命名空间的、以及没有命名空间的，都进 `ns_attrs`**（后者是为了兜住 `package` 这种本来就没命名空间的属性）。

取值时：

```python
def get(self, name, default=None):
    return self.ns_attrs.get(name, self.attrs.get(name, default))
```

**先找 `ns_attrs`，找不到再找 `attrs`，都没有用默认值。** 这就是"优先级"。

`__slots__` 是干嘛的？限定这个类只能有这 6 个属性，**防止手滑写错名字**（比如 `self.atrrs`），同时省内存（不用给每个实例建 `__dict__`）。跑几万个节点时有意义。

### 3.7 栈式建树：`cur` 指针的进与出

解析 XML 最难的不是读字段，是**把平铺的字节序列还原成树结构**。

文件里的顺序是这样的（注意：**只有开始和结束事件，没有"深度"信息**）：

```
[开始] manifest
  [开始] uses-permission
  [结束] uses-permission
  [开始] uses-sdk
  [结束] uses-sdk
  [开始] application
    [开始] activity
    [结束] activity
  [结束] application
[结束] manifest
```

要变成这样：

```
manifest
├── uses-permission
├── uses-sdk
└── application
    └── activity
```

**解法：用一个"当前节点"指针 `cur`，像走迷宫一样。**

```python
root = Node("document")   # 虚拟根，方便统一处理
cur = root

# 遇到 [开始]
node = Node(tag, line, cur)
cur.children.append(node)   # 挂到当前节点下面
cur = node                  # 指针下移，之后的东西都是我的子节点

# 遇到 [结束]
cur = cur.parent            # 指针上移，回到父节点
```

**这就是「栈」的思想**：进入一个标签 = 压栈，离开 = 弹栈。`parent` 指针就是栈里的"上一个"。

一个具体例子，跟着走一遍：

| 读到 | 操作 | cur 变成 |
| --- | --- | --- |
| 开始 manifest | 挂到 document 下，下移 | manifest |
| 开始 uses-permission | 挂到 manifest 下，下移 | uses-permission |
| 结束 uses-permission | 上移 | manifest |
| 开始 application | 挂到 manifest 下，下移 | application |
| 开始 activity | 挂到 application 下，下移 | activity |
| 结束 activity | 上移 | application |
| 结束 application | 上移 | manifest |

**不用递归**（递归读这种流式格式很麻烦），用循环 + 指针，一行 `cur = node` 就完成了"进入"，一行 `cur = cur.parent` 完成"退出"。

### 3.8 `find` 为什么是递归的，以及它埋的雷

```python
def find_all(self, tag):
    out = []
    stack = list(self.children)
    while stack:
        cur = stack.pop()
        if cur.tag == tag:
            out.append(cur)
        stack.extend(cur.children)   # 把子节点也压进去
    return out
```

**这是"深度优先搜索"**：把一个节点的所有子孙都翻一遍，找出名字匹配的。

用在这里是因为：我们只关心"有没有 `uses-permission"、"有没有 `activity`"，**不关心它在第几层**。递归查找最省事。

但**它埋了一个雷，我后来踩了**：

`parse_axml` 返回的是虚拟根 `<document>`，真正的 `<manifest>` 是它的**子节点**。所以：

```python
manifest.get("package")   # ← 在 document 上取 package，当然取不到
```

而 `manifest.find("uses-sdk")` **能取到**，因为 `find` 是递归的，穿透到了真正的 manifest 下面。

结果就是：**权限、组件都正常，唯独包名和版本是空的。** 这个 bug 很阴险——大部分功能正常，只有几个字段错，很容易漏掉。

修复只要一行：

```python
doc = _read_manifest(z)
manifest = doc.find("manifest") or doc   # 取真正的根元素
```

**教训**：递归查找方便，但会让你忘记"层级"这件事。取**自身属性**时必须确保站在正确的节点上。

### 3.9 小结：这个解析器有多"真"

回头看，它做的事情：

1. 认文件类型（`0x0003`）
2. 一块一块遍历（靠 `size` 跳）
3. 解字符串池（去重字典 + UTF-8/UTF-16 双编码 + 变长长度）
4. 建标签树（栈式，靠 `parent` 指针）
5. 解属性（5 个字段 + 6 种值类型还原）
6. 抗混淆（资源 ID 兜底）
7. 容错（越界回退、非法 chunk 跳过）

**这不是"调了个库"，这是按规范实现了一个格式解析器。** 这一段里几乎每个细节都有出处，因为真的踩过 `+16` 那个坑。

## 第四章 `apk_parser.py` —— 拿解析器去干活

有了 `axml.py`，这里就是"业务逻辑"。

### 4.1 先解决一个兼容问题：有些包是明文

```python
raw = z.read("AndroidManifest.xml")
if raw.lstrip().startswith(b"<"):
    # 极少数调试包是明文 XML
    root = ET.fromstring(raw)
```

**为什么会有明文？** 开发阶段用 `aapt` 或某些构建配置，可能保留明文。极少见，但真实存在。

判断方法很朴素：**看第一个非空白字符是不是 `<`**。二进制 XML 第一个字节是 `0x03`，不可能是 `<`。

`lstrip()` 是为了防止文件开头有空格/换行。

**这是防御性编程的典型**：主路径是二进制，但留一条小路给例外，代价只有 3 行代码。

### 4.2 权限：为什么 `split(".")[-1]`

清单里的权限长这样：

```
android.permission.READ_CONTACTS
android.permission.ACCESS_FINE_LOCATION
com.example.custom.SOME_PERMISSION
```

规则库里的 key 是短名（`READ_CONTACTS`），所以：

```python
name = (node.get("name") or "").split(".")[-1]
```

`split(".")` 按点切开，`[-1]` 取最后一段。

**为什么不直接用全名做 key？** 因为有的 App 会自定义权限（`com.xxx.permission.YYY`），全名五花八门，短名归一化后能覆盖更多。

`or ""` 是防御：万一 `get` 返回 `None`，`None.split()` 会崩。

### 4.3 排序：为什么风险高的排前面

```python
order = {"high": 0, "medium": 1, "low": 2}
perms.sort(key=lambda x: order.get(x["level"], 3))
```

**这个细节很能体现"给人看"还是"给机器看"的区别。**

如果按文件里的原始顺序输出，读报告的人要在一堆 `INTERNET`、`VIBRATE`、`WAKE_LOCK` 里翻找 `READ_CONTACTS`。

按风险排序后，**第一眼看到的就是最该看的东西**。

`order.get(x["level"], 3)` 里的 `3` 是兜底：遇到规则库没收录的等级，排到最后，不崩。

### 4.4 `exported` 的三态逻辑（最容易讲错的一处）

这是安卓安全里最经典的坑，也是**这个项目最能体现专业度的地方之一**。

一个组件（Activity / Service / Receiver / Provider）的 `exported` 属性有**三种状态**，不是两种：

| 状态 | 写法 | 是否对外暴露 |
| --- | --- | --- |
| 显式 true | `android:exported="true"` | ✅ 暴露 |
| 显式 false | `android:exported="false"` | ❌ 不暴露 |
| **没写** | 只有 `intent-filter` | ⚠️ **取决于有没有 intent-filter** |

第三种最坑：**安卓的默认规则是"如果你声明了 intent-filter，我就认为你想被外部调用"**（因为 intent-filter 的作用就是"我能响应这类请求"）。

```python
exported_attr = node.get("exported")
has_filter = node.find("intent-filter") is not None
exported = (exported_attr == "true") or (exported_attr is None and has_filter)
```

拆开看：

- `exported_attr == "true"` → 显式声明了，暴露
- `exported_attr is None and has_filter` → 没声明但有问题，按默认规则算暴露
- 其他（显式 false，或没写也没 filter）→ 不暴露

**注意 `exported_attr is None` 不能用 `not exported_attr` 代替。** 因为如果写的是 `"false"`，`not "false"` 是 `False`（字符串非空为真），逻辑会错。**必须严格判断"是不是 None"**。

代码还留了一行注释：

```python
# 未显式声明 exported 时，含 intent-filter 的组件默认对外暴露（API<31）
```

**为什么要提 API 31？** 因为安卓 12（API 31）之后收紧了规则：`exported` 必须显式声明，不声明会**编译报错**。所以这个"默认规则"只对老包有效。写进注释，是为了让读代码的人知道边界在哪。

**这是安全评估里真实的攻击面**：一个没写 `exported`、但带 `intent-filter` 的 Activity，任何 App 都能拉起它，传恶意参数，如果它没做校验，就可能被越权。

### 4.5 URL Scheme：为什么过滤 http/https

```python
if scheme and scheme.lower() != "http" and scheme.lower() != "https":
```

清单里的 `<data>` 标签同时用来声明两件事：

1. **自定义 scheme**（`myapp://`）—— 可以被别的 App 唤起，是**攻击面**
2. **http/https** —— 通常是 `intent-filter` 用于处理网页链接（比如浏览器），**不是自定义协议**，混进来会污染结果

所以我们只留自定义的。样例里输出的 `demoapp`、`demoscheme` 就是自定义的。

`scheme.lower()` 是因为 XML 里可能写成 `HTTP`，大小写不敏感。

### 4.6 SDK 检测：为什么要三种写法

规则库里的一个 SDK 长这样：

```json
{
  "name": "友盟+ 统计",
  "patterns": ["com.umeng.analytics", "com/umeng/analytics", "UMeng"]
}
```

**为什么同一个 SDK 要写三个 pattern？**

因为它在不同地方以不同形式出现：

| 位置 | 实际存的字符串 | 用哪个 pattern |
| --- | --- | --- |
| 配置文件、文档 | `com.umeng.analytics` | 点号版 |
| **dex 里的类名** | `Lcom/umeng/analytics/MobclickAgent;` | **斜杠版** |
| iOS 二进制里的类名 | `UMengAnalytics` | 驼峰版 |

**dex 是重点**：Java 类在 dex 里存成 `L包名/类名;` 的形式（`L` 开头 `;` 结尾，中间用斜杠）。所以搜 `com.umeng.analytics` 搜不到，必须搜 `com/umeng/analytics`。

代码里自动做了转换：

```python
if p.encode("utf-8") in blob or p.replace(".", "/").encode("utf-8") in blob:
```

**一个 pattern，两种形态都试**。这样规则库只需要写点号版，代码负责展开。

**为什么用子串搜索而不是正则？**

```python
if "com/umeng/analytics" in blob
```

因为：
1. 快。一个 50MB 的 dex，正则要几秒，`in` 是 C 层实现的字符串搜索，几十毫秒
2. 稳。类名就是固定字符串，不需要模糊匹配

### 4.7 为什么"文件名"也算证据

```python
names_blob = "\n".join(names).encode("utf-8", errors="ignore")
evidence_blobs.append(("zip-entry-list", names_blob))
```

`names` 是 zip 里所有文件的路径列表。把它们拼成一个大字符串，也当成"待搜索的文本"。

**为什么？** 因为加固特征经常藏在**文件名**里：

```
lib/armeabi-v7a/libjiagu.so     ← 360 加固
lib/armeabi-v7a/libshella.so    ← 腾讯乐固
lib/armeabi-v7a/libnesec.so     ← 网易易盾
```

样例里 `libjiagu.so` 就是这么被识别成"360 加固"的。

**这带来一个副作用，必须承认**：样例同时报告了"梆梆加固"（来自 dex 里的 `com.bangcle`）和"360 加固"（来自文件名 `libjiagu.so`）。**一个 App 通常只穿一件壳**，这里两个都报，是因为我故意在样本里塞了两家的特征。

真实场景下如果同时命中多个壳，说明：
- 可能有二次打包（壳套壳）
- 也可能只是某个 SDK 恰好包含了别人的类名（误报）

**报告里如实列出全部命中，把判断留给分析者**，这比"自动选一个最像的"更诚实。

### 4.8 扫描预算：`max_scan_bytes` 为什么必须有

```python
budget = max_scan_bytes   # 默认 128MB
for n in dex_names:
    if budget <= 0:
        result["notes"].append("dex 扫描超出上限，部分文件已跳过")
        break
    data = z.read(n)
    budget -= len(data)
```

**为什么要有上限？**

因为 `z.read(n)` 是**把整个文件读进内存**。一个 500MB 的巨型 App（尤其是游戏），dex 加 so 可能好几百 MB，全读进去会：

- 内存爆掉（尤其在低配机器上）
- 慢到不能用

128MB 是个折中：**覆盖 99% 的普通 App，同时保证不会把机器搞崩。**

超了怎么办？**不静默跳过，而是在报告里写一句 `notes`**。这很重要——用户看到"SDK 只识别出 2 个"时要能知道"是真的只有 2 个，还是因为预算不够没扫全"。

**这就是"可解释性"**：每个异常都要留下痕迹，不能悄悄吞掉。

## 第五章 `ipa_parser.py` —— 苹果那一侧

iOS 的结构和安卓**完全不一样**，所以是另一个文件。

### 5.1 IPA 也是 zip，但目录有讲究

```
app.ipa (其实是 zip)
└── Payload/
    └── MyApp.app/          ← 真正的 App 本体（.app 其实是个文件夹）
        ├── Info.plist      ← 配置文件（相当于安卓的 Manifest）
        ├── MyApp           ← 主可执行文件（Mach-O 格式，没有后缀！）
        ├── Frameworks/     ← 内嵌的第三方框架
        │   ├── WeChatSDK.framework/
        │   └── UMeng.framework/
        ├── Assets.car      ← 图片资源
        └── PkgInfo
```

**关键区别**：

- 安卓的清单是**二进制 XML**（要自己解析）
- iOS 的配置是 **plist**（Python 标准库 `plistlib` 直接能读，省事）

所以 iOS 侧的技术难点不在"读配置"，在**后面两件事**：认框架、查加密。

### 5.2 目录名推导的坑

第一版代码这样写：

```python
app_dirs = [n for n in names if n.startswith("Payload/") and n.endswith(".app/")]
```

结果报错：`未找到 Payload/*.app/`。

**为什么？** 因为 `zipfile.namelist()` 返回的是**文件路径列表**，如果打包工具没显式写入"目录条目"，就不会有 `Payload/MyApp.app/` 这一项，只有：

```
Payload/MyApp.app/Info.plist
Payload/MyApp.app/MyApp
```

**修复思路：从文件路径反推目录。**

```python
app_dirs = sorted({
    f"Payload/{n.split('/')[1]}/"
    for n in names
    if n.startswith("Payload/") and n.count("/") >= 2
})
```

`n.split('/')[1]` 取第二段（`MyApp.app`），再拼回 `Payload/MyApp.app/`。

**这个坑的通用教训**：zip 里"目录"不是实体，只是路径的前缀。**不要假设目录条目存在**，永远从文件路径推导。

### 5.3 iOS 的"权限"为什么长得不一样

安卓是"申请"模式：

```xml
<uses-permission android:name="android.permission.CAMERA" />
```

iOS 是"说明理由"模式：

```xml
<key>NSCameraUsageDescription</key>
<string>用于扫描二维码</string>
```

**为什么 iOS 要这么设计？** 因为苹果强制要求：**你想用相机，必须在配置里写清楚"为什么用"，这段话会原样弹给用户看。**

```python
for key, value in info.items():
    if key in usage_defs:
        ...
    elif key.endswith("UsageDescription"):   # 规则库没收录的新权限
        perms.append({... "level": "medium", "label": "未分类用途声明" ...})
```

第二分支很关键：**苹果每年加新权限**（比如最近的"本地网络"），规则库不可能永远最新。

`endswith("UsageDescription")` 是个**兜底启发式**：只要是这种命名，就是权限声明，先记下来标"未分类"，不要漏。

**宁可标"未分类"，也不要因为它不在名单里就丢掉。** 这是安全工具的底线——**漏报比误报危险**。

而且我们把 `description` 原文也存下来（截前 120 字）：

```python
"description": str(value)[:120]
```

**为什么？** 因为这段文字本身就是证据。合规检查时经常要看："它说用相机是'扫描二维码'，但代码里其实在拍照上传" —— 声明和实际用途不符，就是违规点。

### 5.4 Framework 计数那个 bug

第一版：

```python
frameworks = {n.split("/")[2] for n in names if n.startswith(f"{app_dir}Frameworks/")}
```

路径 `Payload/MyApp.app/Frameworks/WeChatSDK.framework/WeChatSDK` 切开是：

```
[0] Payload
[1] MyApp.app
[2] Frameworks      ← 取到了这个，不是框架名！
[3] WeChatSDK.framework
[4] WeChatSDK
```

所以两个框架都被算成 `"Frameworks"`，去重后**只剩 1 个**。报告显示"内嵌 Framework: 1"，实际是 2。

修复：**先去掉前缀，再取第一段**。

```python
fw_prefix = f"{app_dir}Frameworks/"
frameworks = {
    n[len(fw_prefix):].split("/")[0]     # 去掉前缀后取第一段
    for n in names
    if n.startswith(fw_prefix) and n[len(fw_prefix):].split("/")[0].endswith(".framework")
}
```

**教训**：**按固定下标取路径段，是最容易出错的写法**。因为路径深度会变。正确做法是先"切掉已知前缀"，再处理剩下的部分。

### 5.5 Mach-O 是什么（这块要讲清楚）

`MyApp` 那个没有后缀的文件，是苹果的可执行文件格式，叫 **Mach-O**（Mach Object）。

**为什么必须懂它？** 因为它决定了"这个包能不能分析"。

#### 5.5.1 文件头：magic number

所有二进制格式开头都有"魔数"，用来验明正身：

```python
_MH_MAGIC_32 = 0xFEEDFACE    # 32 位
_MH_MAGIC_64 = 0xFEEDFACF    # 64 位
_FAT_MAGIC_BE = 0xCAFEBABE   # 胖二进制（多架构合集）
```

这些数字很有意思：`FEEDFACE` 读作 "feed face"（喂脸），`CAFEBABE` 读作 "cafe babe"（咖啡宝贝）—— 上世纪工程师的幽默。

代码判断：

```python
magic_be = struct.unpack_from(">I", data, 0)[0]
if magic_be == _FAT_MAGIC_BE:
```

**注意这里是 `>` 不是 `<`**。为什么？

因为 fat 头是**大端序**（历史遗留），而里面的每个切片是**小端序**。**同一个文件里两种字节序混着用**，这是苹果格式的历史包袱。

```python
if magic_be == 0xcafebabe:      # 大端读，判断 fat
    ...
else:
    _parse_thin_macho(data, 0)  # 内部用小端读
```

#### 5.5.2 thin vs fat：一个盒子 vs 分格盒

- **thin**：只装了一种 CPU 架构的代码（比如只有 arm64）
- **fat**（也叫 universal）：装了多种架构，比如同时有 arm64（真机）和 x86_64（模拟器）

```
fat 文件结构：
┌──────────────────────────┐
│ 头：0xCAFEBABE + 切片数量  │
├──────────────────────────┤
│ 切片表（每个 20 字节）      │
│  ├─ cputype, offset, size │
│  └─ ...                   │
├──────────────────────────┤
│ 切片 1（arm64 的完整 Mach-O）│
├──────────────────────────┤
│ 切片 2（x86_64 的完整 Mach-O）│
└──────────────────────────┘
```

代码：

```python
nfat = struct.unpack_from(">I", data, 4)[0]
for i in range(min(nfat, 8)):        # 最多看 8 个切片，防畸形文件
    off = 8 + i * 20
    cputype, _, slice_off, slice_size, _ = struct.unpack_from(">IIIII", data, off)
    info = _parse_thin_macho(data, slice_off)   # 跳到切片位置再解析
```

**为什么要 `min(nfat, 8)`？** 因为如果文件被损坏，`nfat` 可能是个天文数字，循环会跑到天荒地老。**给循环加硬上限，是解析不可信输入的必备习惯。**

#### 5.5.3 Load Command：头后面的"指令清单"

Mach-O 头之后，是一串 **load command（加载命令）**。可以理解成"给系统看的说明书目录"：

```
LC_SEGMENT_64       ← 我这里有个段（代码段/数据段）
LC_SYMTAB           ← 我的符号表在哪
LC_ENCRYPTION_INFO  ← ★ 我加密了没
LC_LOAD_DYLIB       ← 我依赖哪些动态库
...
```

每个命令开头也是 `cmd + cmdsize`（和 chunk 一模一样的思路）：

```python
for _ in range(ncmds):
    cmd, cmdsize = struct.unpack_from("<II", data, pos)
    if cmd in (_LC_ENCRYPTION_INFO, _LC_ENCRYPTION_INFO_64):
        cryptid = struct.unpack_from("<I", data, pos + 16)[0]
    pos += cmdsize     # 跳到下一个命令
```

#### 5.5.4 `cryptid`：这个数决定你能不能干活

`LC_ENCRYPTION_INFO` 命令里有个 `cryptid` 字段：

| cryptid | 含义 | 对你意味着 |
| --- | --- | --- |
| `0` | 没加密 | ✅ 可以直接反编译、静态分析 |
| `1` | 已加密 | ❌ 代码段是密的，必须先脱壳 |

```python
"encrypted": None if cryptid is None else bool(cryptid)
```

**注意这里用 `None` 表示"不知道"**，而不是 `False`。因为如果整个文件里没找到这个命令（极少见），我们**不能说它没加密**——只能说"没查出来"。

```python
"encrypted": None if cryptid is None else bool(cryptid)
```

**这个区分很重要**：`False`（确认没加密）和 `None`（没查出来）在报告里要区分开。把"未知"当"安全"，是安全领域最常见的错误。

报告里最终输出成三档：

```python
{True: "已加密（App Store 加密，分析前需先脱壳）",
 False: "未加密（cryptid=0，通常已脱壳或企业签）"}.get(..., "未知")
```

**为什么从 App Store 下的包都是加密的？** 因为苹果为了保护开发者，上架时会把可执行文件的 `__TEXT` 段加密。你从手机里 dump 出来的 IPA，必须先脱壳（把解密后的代码从内存里 dump 出来）才能分析。

**这就是为什么工具要告诉你加密状态**——省得你对着一坨加密数据白忙半天。

### 5.6 框架名本身就是证据

```python
blobs.append(("frameworks-list", "\n".join(frameworks).encode(...)))
```

即使框架二进制读不出来，**框架的文件夹名也足够判断 SDK**：

```
WeChatSDK.framework     → 微信
UMeng.framework         → 友盟
Bugly.framework         → Bugly
```

所以把框架名列表也当成"待搜索文本"塞进去。

**这是"低成本高收益"的取证思路**：二进制可能很大、可能加密，但**文件名永远在明处**。

## 第六章 `report.py` —— 为什么输出两种格式

### 6.1 CSV 和 Markdown 各管什么

| 格式 | 谁看 | 用来干什么 |
| --- | --- | --- |
| `汇总.csv` | Excel / 人 | **横向对比一批 App**：哪个 SDK 用得最多、哪类权限最普遍 |
| `<app>-报告.md` | 人 | **单个 App 的完整评估**：可以直接交给客户或评审方 |

**为什么不是只出 JSON？**

JSON 是给机器看的。安全评估的交付物，**最终是给人看的报告**。JSON 只作为中间产物（`--json` 时才输出）。

### 6.2 `utf-8-sig` 是什么，为什么必须用

```python
with out_path.open("w", encoding="utf-8-sig", newline="") as f:
```

**不加 `-sig` 会怎样？** 用 Excel 打开 CSV，中文全是乱码。

**原因**：Excel（尤其中文版 Windows 上的老版本）打开 CSV 时，如果文件没有 BOM，它会**猜编码**，经常猜成 GBK。UTF-8 的中文用 GBK 解码，就是一堆方块和问号。

**BOM（Byte Order Mark）** 是文件开头 3 个看不见的字节：

```
EF BB BF
```

它相当于在文件头上贴个标签："我是 UTF-8"。Excel 看到它就老实了。

**代价**：BOM 会让某些命令行工具（比如 `head`）多显示个 `﻿`。但**给 Excel 用，值得**。

### 6.3 七章结构，每章为什么存在

```
一、基本信息       ← 先确认"我扫的是哪个文件"
二、结论摘要       ← 给人 5 秒判断"这 App 有没有问题"
三、权限清单       ← 证据层 1
四、SDK 清单       ← 证据层 2
五、对外暴露面     ← 证据层 3（安全视角，不是合规视角）
六、合规风险提示   ← 从"有什么"推到"该查什么"
七、检测方法与局限 ← 边界声明
```

**几个设计上的用心**：

**第二章放摘要，不放细节。** 因为读报告的人（HR、客户、领导）通常只看前两屏。必须让他 5 秒内知道结论：

```
- 声明权限/隐私用途共 5 项，其中高风险 4 项
- 识别第三方 SDK 4 个，其中高风险 3 个
- 加固状态：梆梆加固、360 加固
```

**第四章主动写误报说明**：

> SDK 命中基于字符串/文件特征，可能存在误报（如仅引用未集成、或类名巧合）。

**这句话是专业性的体现。** 新手会把"命中了"直接说成"它集成了"，老手会说"命中了，需要人工确认"。**主动承认工具有误报，比假装 100% 准确更可信。**

**第五章是"安全视角"，和合规视角分开。** 导出组件、URL Scheme 这些**不是隐私问题**，是**攻击面问题**。两个视角混在一起，报告会变得不专业。

**第七章程式化地写了局限**，包括那句关键的：

> 静态检测只能看到"声明了什么"，无法证明"是否在用户同意隐私政策之前调用"

**这一章的价值**：它让这份报告从"一个脚本的输出"变成"一份有边界声明的评估文档"。**评估报告必须写明方法和局限，这是行业规范。**

### 6.4 表格转义：一个不起眼但会炸的细节

```python
def _esc(text):
    return str(text).replace("|", "\\|").replace("\n", " ")
```

**为什么？** Markdown 表格用 `|` 分隔列。如果某个值里本身有 `|`（比如权限描述里写了"读|写"），表格结构会**直接崩掉**，整份报告排版全乱。

`\n` 同理：表格单元格里不能有换行，会把行拆断。

**这类"输入可能污染输出格式"的问题，在生成任何文档时都要防。**

## 第七章 `scanner.py` —— 调度员的三个设计

### 7.1 目录递归

```python
if p.is_dir():
    for f in sorted(p.rglob("*")):
        if f.suffix.lower() in {".apk", ".ipa", ".xapk"}:
```

`rglob("*")` 是**递归**列目录（子目录里的也扫）。`sorted` 让输出顺序稳定（否则每次跑顺序不一样，难对比）。

**为什么要支持目录？** 因为真实场景经常是"我下了一堆包，全扫一遍看哪家有 SDK 合规问题"。

### 7.2 为什么单个文件失败不能中断

```python
try:
    result = scan_one(path)
except Exception as e:
    print(f"  [失败] {path.name}: {type(e).__name__}: {e}", file=sys.stderr)
    continue      # ← 关键：继续下一个
```

**如果扫 50 个包，第 3 个损坏了，不捕获异常会怎样？** 整个程序崩掉，前 2 个的结果也没了，后面 47 个没扫。

**批量任务的第一原则：局部失败不影响全局。**

而且错误信息打到 `stderr`（标准错误），正常结果打到 `stdout`（标准输出）——这样你可以：

```bash
python3 scanner.py pkgs/ --out out 2> errors.log    # 错误单独存文件
```

**这是 Unix 工具的基本礼仪**：机器可读的走 stdout，诊断信息走 stderr。

验证过：扔一个假 `.apk`（内容是 "not a zip"）进去，程序报错、跳过、继续扫剩下的，最后 exit code 还是 0。

### 7.3 文件名为什么要加格式后缀

```python
md_path = to_markdown(result, out_dir / f"{path.stem}-{result['format']}-报告.md")
```

**因为 `demo-app.apk` 和 `demo-app.ipa` 的 `stem` 都是 `demo-app`。** 不加格式，两份报告会**互相覆盖**，只剩最后一个。

这个 bug 我在验证时发现了：先扫 APK 生成 `demo-app-报告.md`，再扫 IPA 又生成同名文件，**把 APK 的报告盖掉了**。

修复后变成 `demo-app-apk-报告.md` / `demo-app-ipa-报告.md`，一眼能区分。

**这类"同名覆盖"问题，在批量生成产物时特别常见。**

## 第八章 `tests/make_fixtures.py` —— 自己造样本

### 8.1 为什么需要"造"样本

真实 APK 有两个麻烦：

1. **体积大**（几十上百 MB，不方便放进代码仓库）
2. **版权/隐私问题**（别人的包不能随便传）

所以**自己造一个最小的、合法的样本**，用来验证解析器是否正确。

**这个文件本身就是能力证明**：能"按规范编码"一个格式，说明你真的懂这个格式，而不只是"能读"。

### 8.2 怎么手工编码一个 AXML

思路**和解析完全反过来**：

```
解析：字节 → 树
编码：树 → 字节
```

先写一个"字符串池管理器"：

```python
class StringPoolBuilder:
    def __init__(self):
        self._index = {}      # 字符串 → 编号

    def intern(self, s):
        if s not in self._index:      # 没见过的才分配新编号
            self._index[s] = len(self._index)
        return self._index[s]
```

`intern` 这个名字来自 Python 内置的字符串驻留机制，意思是"**登记**"：第一次见分配编号，之后复用。

**为什么编码时要先"扫描一遍全部字符串"？** 因为字符串池在最前面，**必须先把所有字符串收集齐，才能生成池，然后才能写后面的引用。**

所以 `build_axml` 里先 `walk` 一遍（只为收集字符串），再 `build` 池，最后再 `walk` 一遍写字节。

**这个"两遍扫描"是编译器/编码器的经典模式**（第一遍收集符号，第二遍生成代码）。

长度字段的编码（对应解析时的 `_decode_length8`）：

```python
def _len8(n):
    if n < 0x80:
        return bytes([n])              # 一个字节够
    return bytes([0x80 | (n >> 8), n & 0xFF])   # 两个字节
```

**必须和解析逻辑严格互为逆运算**，否则自己造的文件自己都读不出来。

造 START_ELEMENT：

```python
size = 36 + len(body)     # 36 是固定头大小
out = struct.pack("<HHI", 0x0102, 16, size)
out += struct.pack("<II", line, 0xFFFFFFFF)   # lineNumber, comment
out += struct.pack("<I", 0xFFFFFFFF)          # ns
out += struct.pack("<I", name_idx)
out += struct.pack("<HHH", 20, 20, len(attrs))  # ← 这里写 20
out += struct.pack("<HHH", 0, 0, 0)
out += body
```

注意 `attributeStart` 写的是 `20`，**正好对应解析端 `chunk + 16 + attr_start`**。两边必须一致。

### 8.3 造一个 Mach-O

```python
def _minimal_macho(extra_payload=b""):
    header = struct.pack("<IIIIIII", 0xFEEDFACF, 0x0100000C, 0, 2, 1, 24, 0) + struct.pack("<I", 0)
    load_cmd = struct.pack("<IIIIII", 0x2C, 24, 0, 0, 0, 0)
    return header + load_cmd + extra_payload
```

参数含义：

| 位置 | 值 | 含义 |
| --- | --- | --- |
| magic | `0xFEEDFACF` | 64 位 Mach-O |
| cputype | `0x0100000C` | arm64 |
| filetype | `2` | MH_EXECUTE（可执行文件） |
| ncmds | `1` | 只有 1 个 load command |
| sizeofcmds | `24` | 这个命令 24 字节 |
| cmd | `0x2C` | LC_ENCRYPTION_INFO_64 |
| cryptid | `0` | 没加密 |

**`extra_payload` 是故意塞进去的假 SDK 字符串**（`b"WeChatSDK"`），让特征扫描有东西可命中。

**注意：这个 Mach-O 是"最小可解析"的，不是"能运行的"。** 我们只需要它能被解析器读对，不需要真能跑。**测试夹具的目标是覆盖代码路径，不是模拟真实世界。**

### 8.4 样本里故意埋的"考点"

`make_apk` 造的清单里，我埋了几个**专门用来测边界**的东西：

| 埋的东西 | 测什么 |
| --- | --- |
| 5 个权限（4 高 1 低） | 分级 + 排序是否生效 |
| `activity` 带 `exported=True` | 显式导出能被识别 |
| `provider` 没写 exported 也没 filter | **不该**被算成导出 |
| 两个自定义 scheme + 无 http | scheme 提取 + 过滤 |
| dex 里 4 个 SDK 特征 | 多 SDK 同时命中 |
| `libjiagu.so` 文件名 | 文件名证据链 |
| IPA 里 4 个 UsageDescription | iOS 权限分级 |
| Mach-O `cryptid=0` | 加密状态判定 |

**一个测试样本要覆盖尽可能多的分支，而不是"能跑通就行"。**

实际验证结果：

```
APK: 权限 5 项 / SDK 4 个 / 加固 2 个   ← 全部命中
IPA: 权限 4 项 / SDK 2 个 / 加固 0 个   ← 全部命中
```

## 第九章 规则库为什么用 JSON

### 9.1 不写死在代码里

```python
sdk_defs = rules["sdk"]["sdks"]
```

**如果写死在 Python 里会怎样？**

```python
SDKS = [
    {"name": "友盟", "patterns": [...]},
    ...
]
```

问题：
1. **改规则要改代码**，改代码就可能引入 bug、需要重新测试
2. **非程序员改不了**（安全团队的运营同学想加个 SDK，得找开发）
3. **规则和逻辑混在一起**，代码越写越乱

**分成 `rules/*.json` 之后**：加一个 SDK 就是加一行 JSON，不用碰 Python，不用重测代码。

**这是"配置与逻辑分离"的经典实践。**

### 9.2 `patterns` 三写法的必要性（再说一遍，因为真的很重要）

| 写法 | 场景 |
| --- | --- |
| `com.umeng.analytics` | 配置文件、Android Studio 的依赖声明 |
| `com/umeng/analytics` | **dex 类名的实际存储形式** |
| `UMengAnalytics` | iOS 二进制里的类名 |

**只写一种会漏掉 2/3 的场景。** 这是"跨平台检测"必须处理的差异。

### 9.3 分级的意义

```json
"READ_CONTACTS": {"level": "high", "label": "读取通讯录"},
"INTERNET": {"level": "low", "label": "网络访问"}
```

**为什么不能一律报"有权限"就完事？**

因为**风险是相对的**：

- `INTERNET` 几乎所有 App 都有，报了等于没报（**噪音**）
- `READ_CONTACTS` 只有少数 App 需要，报了就是**信号**

**分级的作用就是"降噪"**：让读者把注意力放在真正敏感的那几条上。

这也解释了报告为什么要**按风险排序**——同一件事，从"给机器看"转成"给人看"时，排序就是信息。

## 第十章 这个工具的边界（必须诚实地说）

### 10.1 静态 ≠ 实际行为

清单声明了权限，**不代表运行时真的调用**。反过来，通过反射、JNI、动态加载调用的东西，**可能完全不体现在清单里**。

**所以这份报告只能说"它申请了什么"，不能说"它做了什么"。**

### 10.2 加固会削弱检测

壳会把 dex 加密，**字符串搜不到**。必须先脱壳（Frida dump 内存里的 dex）再扫。

工具已经能认出壳类型，并在报告里提示这一点——**知道自己被挡住了，也是一种能力**。

### 10.3 特征匹配必然有误报

命中 `com.umeng.analytics` 可能是：
- 真集成了
- 只是某个依赖库引用了
- 类名巧合（虽然概率极低）

**所以报告把"命中"和"实际采集"分开写，不直接下违规结论。**

### 10.4 没覆盖动态加载

插件化框架（如 Tinker、RePlugin）会在运行时下载新 dex，**这些不在静态扫描范围内**。

### 10.5 规则库永远不够全

新 SDK 天天出，新权限年年加。**只能靠持续更新规则库**，或者靠人看到"未分类"时手工补。

**这就是为什么代码里到处是"兜底"分支**：`未分类用途声明`、`attr_0x...`、`notes` 提示。**工具不完美，但要让不完美可见。**

## 附录 名词表（看到不懂的回来查）

| 名词 | 一句话解释 |
| --- | --- |
| **AXML** | Android 二进制 XML。APK 里 `AndroidManifest.xml` 的编译后形态 |
| **Chunk（块）** | 二进制文件的基本单位。开头有 type/size，能一块块跳着读 |
| **字符串池** | 把所有字符串去重存一份、编上号。别处只存编号，省空间 |
| **Res_value** | 属性的"值"结构：类型标签 + 一个 32 位数据 |
| **dex** | Dalvik Executable。Java/Kotlin 编译后的字节码容器 |
| **so** | 共享库（Linux/安卓的动态链接库），C/C++ 编译产物 |
| **加固/壳** | 把代码加密、加反调试，让逆向变难的技术。常见：梆梆、爱加密、360、乐固 |
| **脱壳** | 把加固后的代码还原出来。常用 Frida 从内存 dump |
| **Mach-O** | 苹果的可执行文件格式 |
| **thin / fat** | thin=单一架构；fat=多架构合集（universal binary） |
| **load command** | Mach-O 头后面的"指令清单"，描述段、符号表、加密信息等 |
| **cryptid** | 加密标志。0=没加密，1=App Store 加密（需脱壳） |
| **plist** | 苹果的配置文件格式（XML 或二进制） |
| **Framework** | iOS 的框架（.framework 是个目录），相当于安卓的 aar |
| **exported** | 安卓组件是否允许其他 App 调用。安全评估的核心关注点 |
| **intent-filter** | 组件声明"我能响应哪类请求"。有它往往意味着对外开放 |
| **URL Scheme** | 自定义协议（如 `myapp://`），可被其他 App 唤起 |
| **Frida** | 动态插桩框架，能 hook 函数、改参数、看调用栈。动态分析的主力工具 |
| **hook** | 拦截某个函数的调用，在它执行前后插入自己的代码 |
